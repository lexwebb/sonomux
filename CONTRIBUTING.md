# Contributing to Sonomux 🤝

Thank you for your interest in contributing to **Sonomux**! We want this project to be a welcoming, robust, and community-driven hub for modern audio management on Linux, macOS, and beyond.

Because audio software directly interfaces with physical hardware, kernel audio subsystems, and human ears, we hold code stability, safety, and transparency to high standards.

---

## AI-Assisted Coding Policy 🤖

Sonomux was bootstrapped using modern AI pair programming (collaboration between human maintainers and AI assistants). We embrace AI tools as powerful productivity accelerators, but we maintain strict standards regarding code quality, responsibility, and provenance.

### 1. Human Accountability is Paramount
- **You are the author**: Regardless of whether you wrote code by hand or used an AI assistant (e.g., Claude, Gemini, ChatGPT, GitHub Copilot, Cursor), **you are 100% responsible for every line of code in your pull request**.
- You must understand the logic, memory safety, thread safety, and edge cases of your submission. If asked during review why a design choice was made, *"the AI generated it"* is never an acceptable answer.

### 2. Zero Tolerance for "Prompt-and-Dump" / AI Slop
- **Do not submit unverified AI output**: Pull requests that show clear signs of automated generation without human review—such as hallucinated API methods, nonsensical comments, redundant abstractions, or lack of error handling—will be rejected immediately.
- We value small, focused, deeply understood contributions over large, unvetted AI-generated dumps.

### 3. Real-World Hardware & Safety Verification
- Audio applications interact with real DACs, amplifiers, and headphones. Bugs in volume scaling, routing feedback loops, or thread locks can cause sudden deafening audio spikes or system audio freeze-ups.
- **Mandatory Testing**: All contributions modifying device drivers, routing logic, or volume controls **must be tested on actual hardware or backed by mock unit tests**. You must document your testing environment and results in your pull request.

### 4. Copyright & License Integrity
- You must ensure that any code suggested or generated by AI tools does not reproduce proprietary, non-free, or incompatible third-party code.
- All contributions must be compatible with Sonomux's **GNU General Public License v3.0 (GPL-3.0)**.

## How to Contribute

### 1. Proposing New Features or Hardware Drivers
Before writing large implementations, please [open an issue](https://github.com/lexwebb/sonomux/issues) describing:
- The device or feature you would like to support (e.g., Elgato Wave XLR, Rodecaster, a specific headset).
- The protocol or library needed (USB HID, ALSA, D-Bus, WebSocket).
- Whether you have physical access to the device for testing.

See [docs/DEVICE_CONTRIBUTING.md](docs/DEVICE_CONTRIBUTING.md) for architectural guidelines on implementing device capability traits.

### 2. Development Setup
Make sure you have a working Rust toolchain (edition 2021+):

```bash
git clone https://github.com/lexwebb/sonomux.git
cd sonomux
cargo check --workspace
cargo test --workspace
```

### 3. Code Standards
- **Formatting**: Run `cargo fmt --all` before committing.
- **Linter**: Ensure `cargo clippy --workspace --all-targets` produces no warnings.
- **Documentation**: Public traits, structs, and functions should have clear doc comments explaining their purpose and safety invariants.
- **Test Coverage**: We maintain a **soft boundary of >= 85% line coverage** across the project. Run `./scripts/coverage.sh` before opening a pull request to verify that your changes include unit tests and keep the repository above the target.

### 4. Pull Request Checklist
When opening a PR, include:
- A clear summary of the changes and motivation.
- A list of devices tested (or mock test results).
- Coverage check output (`./scripts/coverage.sh`).
- An explicit note if AI tools were used to draft or assist with the implementation.
